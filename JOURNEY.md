# UniThrift — Integration Journey & Troubleshooting History

This log documents the process, technical issues, attempted solutions, failed paths, and final working strategies encountered during the integration of the **Stitch MCP Design System** into the local **UniThrift** project.

---

## ⚡ Issue 1: PowerShell Script Execution Policies

### Problem
When starting the local web server using `npx -y http-server -p 8080`, PowerShell raised a security error:
> `npx : File C:\Program Files\nodejs\npx.ps1 cannot be loaded because running scripts is disabled on this system.`

This occurs because PowerShell's execution policy restricts running unsigned `.ps1` script wrappers generated by npm/npx installations.

### Things Tried & Failed
* **Direct Execution:** Running standard npm/npx server commands directly from the terminal without special execution parameters failed immediately due to the environment's security policies.

### What Worked
* **Python Server Handoff:** Since Python utilizes standard platform binaries (`python.exe` and built-in standard libraries) instead of scripting wrapper scripts, running:
  ```powershell
  python -m http.server 8080
  ```
  bypassed the PowerShell execution policy check entirely. It created a highly reliable, zero-dependency local static web server.

## 🎨 Issue 2: Stitch CSS Framework Mapping to Vanilla CSS

### Problem
The Stitch mockups used Tailwind CSS styles (classes like `bg-surface/60`, `backdrop-blur-xl`, `font-body-md`, `gap-stack-lg`). The local codebase was purely built on custom Vanilla CSS.

### Things Tried & Failed
* **Direct Class Copying:** Copying Tailwind layout code without linking the Tailwind engine makes styles fail to render.
* **Adding Full Tailwind CDN:** Importing the complete Tailwind CDN can override custom style hierarchies and cause visual conflicts with existing custom elements.

### What Worked
* **Direct Token Translation:** We extracted the JSON configuration from Stitch's style declarations and mapped them to native CSS Custom Properties (`:root` variables) in `styles.css`:
  ```css
  --surface: #0b1326;
  --primary: #6bfb9a;
  --radius-xl: 24px;
  ```
  We manually mapped classes like `.listing-card-mini` and `.housing-card` to use standard, semantic vanilla CSS declarations leveraging those custom properties. This maintained absolute consistency with Stitch design guidelines without introducing framework dependency bloat.

## 🔄 Issue 3: Dynamic State Alignment

### Problem
The original page featured direct section rendering, while the Stitch design combined marketplace listings, PG accommodations, and flatmate matching under a single dynamic segmented feed view.

### Things Tried & Failed
* **Complete Template Replacement:** Replacing the entire HTML structure with the raw screen HTML from Stitch would lose local interactive functions (e.g., college search, branch selection, and item postings).

### What Worked
* **Component-Level Modular Assembly:** We reconstructed `index.html` section by section. We added the segmented feed container at the top of the body, then mapped separate content panels (`thrift-content`, `pg-content`, `flatmate-content`).
* **JavaScript Event Listeners:** In `app.js`, we integrated sliding indicator animations and added rendering routines (`renderBentoGrid()`, `renderHousingGrid()`, `openPgModal()`) to support dynamic switching without discarding original operational systems.
